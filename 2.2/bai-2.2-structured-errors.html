Bài tập 2.2 — Structured Error Responses cho cả 4 loại lỗi

Domain 2 · Tool Design & MCP Integration · Mục 2.2 Structured Error Responses
Người thực hiện: TruongNQ · Ngày nộp: 13/10/2026

1. Mục tiêu

Xây một MCP server có tool tra khách và hoàn tiền, trả lỗi có cấu trúc cho đủ 4 loại (transient, validation, business, permission), tách bạch kết quả rỗng hợp lệ với lỗi truy cập, rồi viết vòng hồi phục rẽ nhánh theo metadata. Cùng bộ kịch bản được chạy lại với lỗi kiểu cũ (chỉ chữ "Error") để thấy agent mất phương hướng ra sao.

Bài này chạy thật được không cần model. Vòng hồi phục ở recovery_agent.rb là logic tất định bằng code, server là MCP stdio thật, nên log ở mục 7 là đầu ra thật. Phần để Claude tự quyết dựa vào metadata (run_llm.sh) là tuỳ chọn và chưa chạy (mục 8).

2. Sơ đồ

3. Năm bước ↔ cách hiện thực

#Yêu cầuHiện thực
1MCP tool tra khách trên DB giả, có tham số kích hoạt lỗi theo yêu cầusupport_mcp_server.rb (stdio, JSON-RPC 2.0, Ruby thuần). get_customer(customer_id, simulate?) với simulate = none | timeout | flaky:N | permission; thêm process_refund(customer_id, amount) để có lỗi business. DB giả 3 khách, CUS-0777 là hồ sơ tài chính bị hạn chế
2Bốn lỗi: timeout, sai định dạng, hoàn tiền vượt hạn mức, bị từ chối quyềntransient_timeout, validation_bad_id, business trong process_refund (> 500 USD), permission_denied. Tất cả isError: true, chỉ transient có isRetryable: true
3Metadata đúng 3 field: category, retry, description gợi ý bước tiếptool_error đặt {errorCategory, isRetryable, description} vào structuredContent và lặp lại dạng JSON trong content (cho client chỉ đọc text). Mỗi description nói rõ vì sao và làm gì tiếp
4Rỗng hợp lệ khác hẳn lỗi truy cậpvalid_empty: isError: false, resultCount: 0, message "truy vấn đã chạy, không cần gọi lại". Lỗi truy cập: isError: true, transient, retryable. Hai bên không chung key nào (test kiểm tra)
5Vòng agent rẽ nhánh: transient ≤ 3 lần có backoff, validation sửa input, business escalate, permission xin quyềnrecovery_agent.rb → handle_structured. Backoff 0.2 → 0.4 → 0.8s. Validation chuẩn hoá "cus 12" → CUS-0012. Business tạo handoff (mã khách, số tiền, lý do). Không bao giờ gọi lại business/permission. Có thêm kịch bản lan truyền lỗi tra 3 khách

Quy ước đếm: 1 lần gọi đầu + tối đa 3 lần retry = tối đa 4 lần gọi cho lỗi transient. Lần gọi lại sau khi sửa input validation là lần gọi mới, không tính là retry.

Lưu ý: errorCategory, isRetryable, description là quy ước của ứng dụng, không có trong MCP spec. CallToolResult của MCP chỉ định nghĩa content, structuredContent, isError. Đề thi dùng 4 loại và cờ retry này, nhưng đừng nói chúng là "trường chuẩn của MCP".
Vì sao customer_id không có pattern trong inputSchema? Nếu schema chặn định dạng, client/SDK có thể từ chối ngay ở lớp giao thức: tool không chạy, agent không nhận được lỗi validation có hướng dẫn sửa. Bài này kiểm định dạng trong code để trả lỗi validation có cấu trúc. (Ngược lại, thiếu hẳn tham số bắt buộc thì server trả JSON-RPC error, minh hoạ lớp 1.)

5. Rỗng hợp lệ ≠ lỗi truy cập

Rỗng hợp lệ (CUS-9999 không tồn tại)
{
  "isError": false,
  "structuredContent": {
    "results": [

    ],
    "resultCount": 0,
    "message": "Truy vấn đã chạy thành công, không có khách nào có mã CUS-9999. Không cần gọi lại."
  }
}
Truy vấn ĐÃ chạy. Trả lời "không tìm thấy", không gọi lại.
Lỗi truy cập (DB timeout)
{
  "isError": true,
  "structuredContent": {
    "errorCategory": "transient",
    "isRetryable": true,
    "description": "Kết nối DB khách hàng bị timeout sau 5s, truy vấn CHƯA chạy (dữ liệu có thể vẫn tồn tại). Yêu cầu hợp lệ: gọi lại nguyên văn sau vài trăm ms."
  }
}
Truy vấn CHƯA chạy, dữ liệu có thể tồn tại. Gọi lại có backoff.

Nếu hai trường hợp trông giống nhau (bản bad trả "Error" cho cả hai), agent sẽ retry 3 lần một khách không tồn tại rồi escalate vô ích: đúng tình huống trong câu luyện tập của bài.

6. Structured so với "Error" (kết quả thật)

Cùng 10 kịch bản, chạy với ERROR_STYLE=structured và ERROR_STYLE=bad. Agent ở bản bad không có metadata nên chỉ còn cách đoán: thử lại 3 lần rồi chuyển người.

Bản bad: retry vô ích khách không tồn tại, gọi hoàn tiền 750 USD tới 4 lần (với hệ thống thật đây là rủi ro), không tự sửa được "cus 12", và mọi thứ đổ về cho người. Kịch bản lan truyền lỗi: bản structured báo coordinator found / not_found / failed tách riêng; bản bad xếp luôn khách không tồn tại vào nhóm lỗi.

#!/usr/bin/env ruby
# frozen_string_literal: true

# Bài 2.2 – MCP server "support" (stdio, JSON-RPC 2.0, Ruby thuần, không cần gem).
#
# Hai tool:
#   get_customer(customer_id, simulate?)  – tra hồ sơ khách trong DB giả
#   process_refund(customer_id, amount)   – hoàn tiền, hạn mức tự động 500 USD
#
# Hai lớp lỗi:
#   1. Protocol error (JSON-RPC `error`): tool không tồn tại, thiếu tham số bắt buộc. Không có tool nào chạy,
#      model không nhận được tool result. Sửa ở schema/client, không phải ở vòng hồi phục của agent.
#   2. Tool execution error (`result.isError: true`): tool đã chạy nhưng thất bại. Metadata nằm trong
#      structuredContent: { errorCategory, isRetryable, description }. Đây là QUY ƯỚC CỦA ỨNG DỤNG,
#      MCP spec chỉ định nghĩa content / structuredContent / isError.
#
# Lưu ý: customer_id KHÔNG khai báo `pattern` trong inputSchema. Nếu schema chặn định dạng thì client/SDK
# có thể từ chối ngay ở lớp giao thức và agent không bao giờ thấy lỗi validation có hướng dẫn sửa.
# Định dạng được kiểm trong code để trả lỗi validation có cấu trúc.
#
# Tham số simulate (chỉ để kích hoạt lỗi theo yêu cầu):
#   none (mặc định) | timeout (luôn timeout) | flaky:N (N lần đầu timeout, sau đó chạy bình thường)
#   | permission (giả lập service account bị thu quyền)
#
# Biến môi trường:
#   ERROR_STYLE=structured (mặc định) | bad   – bad: mọi lỗi chỉ là chuỗi "Error", kết quả rỗng cũng là "Error"
#   SUPPORT_LOG=<file>                         – mỗi tools/call ghi 1 dòng JSON

require "json"
require "time"

ERROR_STYLE = ENV.fetch("ERROR_STYLE", "structured")
LOG_FILE = ENV["SUPPORT_LOG"]
REFUND_LIMIT = 500

# Dữ liệu GIẢ.
CUSTOMERS = {
  "CUS-0012" => { customer_id: "CUS-0012", name: "Nguyễn Thị Lan", tier: "Vàng", balance_usd: 120.0,
                  orders: ["#12345", "#31007"], restricted: false },
  "CUS-0042" => { customer_id: "CUS-0042", name: "Trần Văn Minh", tier: "Bạc", balance_usd: 0.0,
                  orders: ["#20871"], restricted: false },
  # Hồ sơ thuộc nhóm tài chính bị hạn chế: service account của agent không có quyền đọc.
  "CUS-0777" => { customer_id: "CUS-0777", name: "Công ty TNHH Hoà Phát Đạt", tier: "Doanh nghiệp",
                  balance_usd: 15_400.0, orders: ["#45210"], restricted: true }
}.freeze

TOOLS = [
  { name: "get_customer",
    description: <<~DESC.strip,
      Tra hồ sơ khách hàng theo mã khách dạng CUS-NNNN (vd CUS-0012): tên, hạng, số dư, danh sách mã đơn.
      Không có khách khớp thì trả kết quả rỗng (resultCount = 0, KHÔNG phải lỗi): đừng gọi lại, hãy báo không tìm thấy.
      Khi lỗi, structuredContent có errorCategory, isRetryable, description: làm theo description.
    DESC
    inputSchema: { type: "object",
                   properties: {
                     customer_id: { type: "string", description: "Mã khách dạng CUS-NNNN, vd CUS-0012" },
                     simulate: { type: "string", description: "Chỉ dùng khi test: none | timeout | flaky:N | permission" }
                   },
                   required: ["customer_id"] } },
  { name: "process_refund",
    description: <<~DESC.strip,
      Hoàn tiền cho khách (USD). Tự động duyệt tối đa #{REFUND_LIMIT} USD; vượt hạn mức trả lỗi business, không gọi lại mà chuyển quản lý duyệt.

    inputSchema: { type: "object",
                   properties: {
                     customer_id: { type: "string", description: "Mã khách dạng CUS-NNNN" },

                   },
                   required: ["customer_id", "amount"] } }
].freeze

ID_FORMAT = /\ACUS-\d{4}\z/
$flaky_counts = Hash.new(0) # (customer_id, simulate) → số lần đã gọi, để flaky:N hết lỗi sau N lần

def log_call(name, args)
  return unless LOG_FILE

  File.open(LOG_FILE, "a") { |f| f.puts JSON.generate({ at: Time.now.iso8601(3), tool: name, arguments: args }) }
end

# ---- Hai kiểu trả lỗi -------------------------------------------------------------------------

def tool_error(category, retryable, description)
  return { content: [{ type: "text", text: "Error" }], isError: true } if ERROR_STYLE == "bad"

  meta = { errorCategory: category, isRetryable: retryable, description: description }
  { content: [{ type: "text", text: JSON.generate(meta) }], structuredContent: meta, isError: true }
end

def tool_ok(data)
  { content: [{ type: "text", text: JSON.generate(data) }], structuredContent: data, isError: false }
end

def valid_empty(customer_id)
  # Bản bad: "không có kết quả" trông y hệt lỗi, agent không phân biệt được.
  return { content: [{ type: "text", text: "Error" }], isError: true } if ERROR_STYLE == "bad"

  tool_ok({ results: [], resultCount: 0,
            message: "Truy vấn đã chạy thành công, không có khách nào có mã #{customer_id}. Không cần gọi lại." })
end

# ---- Các lỗi theo 4 loại ----------------------------------------------------------------------

def transient_timeout
  tool_error("transient", true,
             "Kết nối DB khách hàng bị timeout sau 5s, truy vấn CHƯA chạy (dữ liệu có thể vẫn tồn tại). " \
             "Yêu cầu hợp lệ: gọi lại nguyên văn sau vài trăm ms.")
end

def validation_bad_id(raw)
  tool_error("validation", false,
             "customer_id '#{raw}' sai định dạng. Định dạng đúng: CUS + gạch ngang + 4 chữ số, vd CUS-0012. " \
             "Gọi lại y nguyên sẽ lỗi tiếp: hãy sửa input rồi gọi lại, hoặc hỏi lại khách mã đúng.")
end

def permission_denied(customer_id)
  tool_error("permission", false,
             "Service account support-bot không có quyền đọc hồ sơ tài chính của #{customer_id}. " \
             "Gọi lại với cùng tài khoản sẽ vẫn bị từ chối: chuyển cho nhân viên cấp cao có quyền finance-read.")
end

def simulated_failure(customer_id, simulate)
  case simulate
  when nil, "", "none" then nil
  when "timeout" then transient_timeout
  when "permission" then permission_denied(customer_id)
  when /\Aflaky:(\d+)\z/
    key = [customer_id, simulate]
    $flaky_counts[key] += 1
    $flaky_counts[key] <= Regexp.last_match(1).to_i ? transient_timeout : nil
  else
    tool_error("validation", false,
               "simulate '#{simulate}' không hợp lệ. Giá trị cho phép: none, timeout, flaky:N, permission.")
  end
end

def get_customer(args)
  id = args["customer_id"].to_s
  return validation_bad_id(id) unless id.match?(ID_FORMAT)

  failure = simulated_failure(id, args["simulate"])
  return failure if failure

  customer = CUSTOMERS[id]
  return valid_empty(id) unless customer
  return permission_denied(id) if customer[:restricted]

  tool_ok({ results: [customer.reject { |k, _| k == :restricted }], resultCount: 1 })
end

def process_refund(args)
  id = args["customer_id"].to_s
  amount = args["amount"]
  return validation_bad_id(id) unless id.match?(ID_FORMAT)
  unless amount.is_a?(Numeric) && amount.positive?
    return tool_error("validation", false, "amount '#{amount}' không hợp lệ: phải là số dương (USD), vd 49.5.")
  end

  customer = CUSTOMERS[id]
  unless customer
    return tool_error("validation", false,
                      "Không có khách #{id} nên không thể hoàn tiền. Kiểm tra lại mã khách bằng get_customer trước.")
  end
  return permission_denied(id) if customer[:restricted]

  if amount > REFUND_LIMIT
    return tool_error("business", false,
                      "Khoản hoàn #{format('%.2f', amount)} USD vượt hạn mức tự động #{REFUND_LIMIT} USD, cần quản lý duyệt. " \
                      "KHÔNG gọi lại: tạo yêu cầu duyệt cho quản lý kèm mã khách, số tiền, lý do; " \
                      "báo khách rằng yêu cầu đang chờ duyệt trong 1 ngày làm việc.")
  end

  tool_ok({ refund_id: "RF-#{id[-4..]}-#{(amount * 100).to_i}", customer_id: id, amount_usd: amount,
            status: "approved" })
end

def call_tool(name, args)
  log_call(name, args)
  case name
  when "get_customer" then get_customer(args)
  when "process_refund" then process_refund(args)
  end
end

# ---- JSON-RPC ---------------------------------------------------------------------------------

def respond(id, result) = $stdout.puts(JSON.generate({ jsonrpc: "2.0", id: id, result: result }))

def respond_error(id, code, message)
  $stdout.puts(JSON.generate({ jsonrpc: "2.0", id: id, error: { code: code, message: message } }))
end

$stdout.sync = true
$stdin.each_line do |line|
  next if line.strip.empty?

  begin
    msg = JSON.parse(line)
  rescue JSON::ParserError
    respond_error(nil, -32_700, "Parse error")
    next
  end
  id = msg["id"]
  case msg["method"]
  when "initialize"
    respond(id, { protocolVersion: msg.dig("params", "protocolVersion") || "2025-06-18",
                  capabilities: { tools: {} }, serverInfo: { name: "support", version: "1.0.0" } })
  when "notifications/initialized", "notifications/cancelled"
    nil
  when "ping"
    respond(id, {})
  when "tools/list"
    respond(id, { tools: TOOLS })
  when "tools/call"
    name = msg.dig("params", "name")
    args = msg.dig("params", "arguments") || {}
    tool = TOOLS.find { |t| t[:name] == name }
    # Lớp 1 – protocol error: tool không tồn tại hoặc thiếu tham số bắt buộc → tool không chạy.
    if tool.nil?
      respond_error(id, -32_602, "Unknown tool: #{name}")
    elsif (missing = tool[:inputSchema][:required] - args.keys).any?
      respond_error(id, -32_602, "Invalid params for #{name}: missing #{missing.join(', ')}")
    else
      respond(id, call_tool(name, args))
    end
  else
    respond_error(id, -32_601, "Method not found: #{msg['method']}") unless id.nil?
  end
end

#!/usr/bin/env ruby
# frozen_string_literal: true

# Bài 2.2 – Vòng hồi phục đọc metadata lỗi và rẽ nhánh.
#
# Đây là logic TẤT ĐỊNH bằng code: không gọi model, nên chạy thật được ngay. Nó đóng vai phần
# "agent" quyết định sau mỗi tool result. (Phần để LLM tự quyết dựa vào cùng metadata: xem run_llm.sh.)
#
#   isRetryable = true  (transient)  → gọi lại nguyên văn, tối đa 3 lần, backoff 0.2s → 0.4s → 0.8s
#   validation                       → sửa input (chuẩn hoá mã khách) rồi gọi lại 1 lần; không sửa được → hỏi lại khách
#   business                         → KHÔNG gọi lại, escalate kèm handoff (mã khách, số tiền, lý do)
#   permission                       → KHÔNG gọi lại, xin quyền cao hơn / chuyển nhân viên có quyền
#   isError=false, resultCount=0     → kết quả rỗng hợp lệ: trả lời "không tìm thấy", KHÔNG gọi lại
#   JSON-RPC error (lớp giao thức)    → tool không chạy: lỗi ở schema/client, báo dev, không vòng hồi phục
#
# Quy ước đếm: 1 lần gọi đầu + tối đa 3 lần retry = tối đa 4 lần gọi cho lỗi transient.
#
# Chạy:  ruby recovery_agent.rb                 # bản structured rồi bản bad, in bảng so sánh
#        ruby recovery_agent.rb structured|bad   # chỉ một bản
#        BACKOFF_SCALE=0.01 ruby recovery_agent.rb   # chạy nhanh (delay ×0.01)

require "json"
require "open3"

SERVER = File.join(__dir__, "support_mcp_server.rb")
MAX_RETRIES = 3
BASE_DELAY = 0.2
BACKOFF_SCALE = Float(ENV.fetch("BACKOFF_SCALE", "1"))

class McpClient
  attr_reader :calls

  def initialize(error_style)
    env = { "ERROR_STYLE" => error_style }
    env["SUPPORT_LOG"] = ENV["SUPPORT_LOG"] if ENV["SUPPORT_LOG"]
    @stdin, @stdout, @wait = Open3.popen2(env, RbConfig.ruby, SERVER)
    @id = 0
    @calls = 0
    rpc("initialize", { protocolVersion: "2025-06-18", capabilities: {}, clientInfo: { name: "recovery-agent" } })
    @stdin.puts JSON.generate({ jsonrpc: "2.0", method: "notifications/initialized" })
  end

  def rpc(method, params)
    @id += 1
    @stdin.puts JSON.generate({ jsonrpc: "2.0", id: @id, method: method, params: params })
    JSON.parse(@stdout.gets)
  end

  def call_tool(name, args)
    @calls += 1
    rpc("tools/call", { name: name, arguments: args })
  end

  def close
    @stdin.close
    @wait.value
  end
end

# Thử sửa mã khách sai định dạng: "cus 12", "cus-0012", "CUS12" → "CUS-0012". Không đoán được thì nil.
def fix_customer_id(raw)
  m = raw.to_s.strip.match(/\Acus[\s\-_]*(\d{1,4})\z/i)
  m && format("CUS-%04d", m[1].to_i)
end

def metadata_of(result)
  result["structuredContent"] || (JSON.parse(result.dig("content", 0, "text").to_s) rescue nil)
end

# ---- Agent đọc metadata -----------------------------------------------------------------------

def handle_structured(client, tool, args, log)
  retries = 0
  fixed = false
  delays = []
  loop do
    resp = client.call_tool(tool, args)
    if resp["error"]
      log << "  ✗ lớp giao thức #{resp['error']['code']}: #{resp['error']['message']} → tool không chạy, báo dev sửa schema/client"
      return { outcome: :protocol_error, delays: delays }
    end

    result = resp["result"]
    meta = metadata_of(result)
    unless result["isError"]
      if meta["resultCount"]&.zero?
        log << "  ○ rỗng hợp lệ (isError=false, resultCount=0) → trả lời khách: không tìm thấy, KHÔNG gọi lại"
        return { outcome: :not_found, delays: delays }
      end
      log << "  ✓ thành công: #{JSON.generate(meta)[0, 110]}"
      return { outcome: :success, data: meta, delays: delays }
    end

    category = meta["errorCategory"]
    log << "  ! #{category} (isRetryable=#{meta['isRetryable']}): #{meta['description'][0, 90]}…"
    if meta["isRetryable"]
      if retries >= MAX_RETRIES
        log << "  ✗ hết #{MAX_RETRIES} lần retry → báo lên: đã thử #{client.calls} lần, lỗi transient, chưa có dữ liệu"
        return { outcome: :gave_up, attempted: retries + 1, delays: delays }
      end
      delay = BASE_DELAY * (2**retries) * BACKOFF_SCALE
      retries += 1
      delays << delay
      log << "    ↻ retry #{retries}/#{MAX_RETRIES} sau #{format('%.2f', delay / BACKOFF_SCALE)}s"
      sleep delay
      next
    end

    case category
    when "validation"
      candidate = fix_customer_id(args["customer_id"])
      if !fixed && candidate && candidate != args["customer_id"]
        log << "    ✎ sửa input customer_id '#{args['customer_id']}' → '#{candidate}' rồi gọi lại (lần gọi mới, không phải retry)"
        args = args.merge("customer_id" => candidate)
        fixed = true
        next
      end
      log << "  ? không tự sửa được → hỏi lại khách mã đúng (dạng CUS-NNNN)"
      return { outcome: :ask_user, delays: delays }
    when "business"
      handoff = { customer_id: args["customer_id"], amount_usd: args["amount"], reason: meta["description"],
                  recommended_action: "Quản lý duyệt hoàn tiền vượt hạn mức" }
      log << "  ⇧ escalate cho quản lý, KHÔNG retry. Handoff: #{JSON.generate(handoff)[0, 120]}…"
      return { outcome: :escalated, handoff: handoff, delays: delays }
    when "permission"
      log << "  🔑 xin quyền finance-read / chuyển nhân viên cấp cao, KHÔNG retry với cùng tài khoản"
      return { outcome: :need_credentials, delays: delays }
    else
      log << "  ✗ errorCategory lạ '#{category}' → escalate"
      return { outcome: :escalated, delays: delays }
    end
  end
end

# ---- Agent "ngây thơ" với lỗi kiểu cũ: chỉ biết isError + chữ "Error" ---------------------------
# Không có category hay isRetryable, cách duy nhất là đoán: thử lại 3 lần rồi chuyển người.

def handle_naive(client, tool, args, log)
  retries = 0
  delays = []
  loop do
    resp = client.call_tool(tool, args)
    if resp["error"]
      log << "  ✗ lớp giao thức: #{resp['error']['message']}"
      return { outcome: :protocol_error, delays: delays }
    end
    result = resp["result"]
    unless result["isError"]
      log << "  ✓ thành công"
      return { outcome: :success, delays: delays }
    end
    log << "  ! \"#{result.dig('content', 0, 'text')}\" (không biết loại lỗi, không biết có nên thử lại)"
    if retries >= MAX_RETRIES
      log << "  ⇧ thử #{client.calls} lần vẫn lỗi → chuyển người xử lý"
      return { outcome: :escalated, delays: delays }
    end
    delay = BASE_DELAY * (2**retries) * BACKOFF_SCALE
    retries += 1
    delays << delay
    log << "    ↻ đoán là lỗi tạm thời, thử lại #{retries}/#{MAX_RETRIES}"
    sleep delay
  end
end

# Mỗi kịch bản một server mới để bộ đếm flaky và số lần gọi tách bạch.
def run_scenario(style, sc)
  client = McpClient.new(style)
  log = []
  result = style == "bad" ? handle_naive(client, sc[:tool], sc[:args].dup, log) : handle_structured(client, sc[:tool], sc[:args].dup, log)
  result.merge(calls: client.calls, log: log)
ensure
  client&.close
end

# Lan truyền lỗi có chọn lọc: tra nhiều khách, khách nào lỗi hết retry thì báo lên kèm kết quả phần còn lại.
def run_batch(style)
  ids = [["CUS-0012", nil], ["CUS-0042", "timeout"], ["CUS-9999", nil]]
  client = McpClient.new(style)
  found = []
  failed = []
  empty = []
  log = []
  ids.each do |id, sim|
    args = { "customer_id" => id }
    args["simulate"] = sim if sim
    r = style == "bad" ? handle_naive(client, "get_customer", args, log) : handle_structured(client, "get_customer", args, log)
    case r[:outcome]
    when :success then found << id
    when :not_found then empty << id
    else failed << { customer_id: id, outcome: r[:outcome] }
    end
  end
  report = { searched: ids.size, found: found, not_found: empty, failed: failed, total_calls: client.calls }
  { report: report, log: log }
ensure
  client&.close
end

def run_style(style)
  puts "\n================ ERROR_STYLE=#{style} ================"
  SCENARIOS.map do |sc|
    r = run_scenario(style, sc)
    puts "\n[#{sc[:id]}] #{sc[:name]}  (#{sc[:tool]} #{JSON.generate(sc[:args])})"
    r[:log].each { |l| puts l }
    puts "  → kết cục: #{r[:outcome]} sau #{r[:calls]} lần gọi"
    [sc[:id], r]
  end.to_h
end

10. Tiêu chí hoàn thành

  • MCP server chạy được, kích hoạt được từng loại lỗi (simulate, dữ liệu, số tiền)
  • Mỗi lỗi có isError: true, đúng category, chỉ transient có isRetryable: true, description nêu vấn đề và bước tiếp
  • Metadata đúng 3 field; business đánh dấu không retry và chỉ sang escalate
  • Rỗng hợp lệ (isError: false, resultCount: 0) khác hẳn lỗi truy cập
  • Vòng agent rẽ nhánh đúng, transient ≤ 3 retry với delay tăng dần, không bao giờ retry business/permission

11. Bài học rút ra

  • Hai lớp lỗi: protocol error (tool không chạy, sửa schema/client) khác tool execution error (tool chạy rồi thất bại, model tự quyết dựa vào isError + metadata).
  • Đọc isRetryable trước, errorCategory sau. false nghĩa là "đừng gửi lại y nguyên", không phải "bỏ cuộc".
  • Rỗng hợp lệ không phải lỗi. Đây là điểm quan trọng nhất của domain: lẫn lộn hai thứ gây retry lãng phí và escalate sai.
  • Lan truyền có chọn lọc: subagent tự retry lỗi tạm thời; chỉ báo lên thứ không tự xử lý được, kèm kết quả một phần và những gì đã thử.

Bẫy đề

  1. Retry kết quả rỗng hợp lệ (tăng retry limit, nới ngưỡng escalate đều sai).
  2. Thông báo lỗi chung chung, không có category / retry / description.
  3. Coi lỗi business là retryable.
  4. Đánh dấu validation isRetryable: true chỉ vì agent sửa được (gửi lại y nguyên vẫn lỗi).
  5. Hiểu isRetryable: false là bỏ task.
  6. Subagent nuốt lỗi, trả rỗng như thành công: coordinator không phân biệt "không có" với "không tìm được".

Ngoài ra: cấm retry hoàn toàn trong system prompt (phương án B của câu luyện tập) là sửa quá tay, chặn cả retry chính đáng cho lỗi tạm thời.
